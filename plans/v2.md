# eversh v2 boundary

Status: bounded candidate list and permanent exclusions | Last updated: 2026-08-21

Historical record: statements about the former `everlink` name or the
superseded one-shot/no-replay transport describe their era. The current
contract is `plans/design.md` revision 2 with bounded association resume.

This document separates measurable future candidates from permanent core non-goals. Nothing here is a v2 commitment. A candidate enters implementation only after a written problem statement, evidence that v1 cannot solve the problem, a security and licence review, a bounded design, and passing measurement gates.

## Permanent core non-goals

These are never added to the everpty or everlink core, even in v2:

- Remote scrollback, terminal parsing, virtual screens, terminal-state snapshots, or screen restoration.
- Local prediction, local echo, terminal datagram synchronization, or Mosh-compatible terminal state.
- Application output replay, input replay, exactly-once delivery across connections, or resumption of an expired SSH stream.
- Per-observer virtual terminal viewports, independent observer resize state, or server-side rendering.
- A second SSH implementation, alternate user or host identity system, or eversh-owned authentication.
- Terminal logs, output archives, keystroke capture, or remote session transcripts.
- A relay, account, public gateway, or arbitrary open proxy in the everlink core.
- A second async runtime in everlink or Tokio/noq in the everpty core.
- A data-relay loop or terminal parser in eversh.
- GPL, AGPL, or custom-restricted production code that cannot be distributed under MIT OR Apache-2.0.

A future product that needs these behaviors must sit above the raw everpty and everlink primitives with a separately reviewed contract, storage policy, and licence.

## Candidate A: broader platform support

Potential scope is macOS and Windows PTY/session support while preserving the same opaque-byte, one-writer, observer, drain/discard, and no-replay contract. It is not a promise of terminal-model compatibility.

Entry gate: implement platform-specific PTY and process-group adapters behind the existing everpty contract, establish socket and permission equivalents, and run the complete byte, ownership, signal, resize, termios/console, cleanup, and resource test suite on each supported platform.

Measurement gate: startup/attach/kill correctness, descriptor/process cleanup, arbitrary-byte fidelity, resize behavior, and idle resource use must meet the documented Linux-equivalent acceptance criteria for each platform. A platform that cannot preserve the contract remains unsupported.

## Candidate B: relays and rendezvous

Potential scope is an optional deployment service for hosts without directly reachable UDP, with explicit operator ownership and no terminal or SSH semantics. It must carry opaque everlink packets only and must not become a public unauthenticated proxy.

Entry gate: document the threat model, tenant isolation, abuse controls, endpoint discovery, key material, observability, retention, failure semantics, and operational owner. The client must remain compatible with direct UDP and ZeroTier/Tailscale operation.

Measurement gate: compare direct, overlay, and relay recovery, latency, packet loss, bandwidth, CPU, memory, and failure blast radius under controlled tests. No relay is added if the overlay baseline meets the supported use case.

## Candidate C: measured path policy

Potential scope is explicit path selection or migration policy when standard single-path QUIC migration is insufficient on supported networks. This is not permission to enable QAD, multipath, QNT, or custom NAT traversal by default.

Entry gate: reproduce a v1 failure with packet captures and a deterministic test, identify the missing standard behavior, and verify that the selected Rust QUIC library supports the needed feature without a second runtime or application replay.

Measurement gate: demonstrate recovery and resource behavior against the v1 baseline, including path validation, spoof resistance, memory, CPU, fairness, and shutdown. A feature that merely exists in the library does not pass the gate.

## Candidate D: managed installation and upgrades

Potential scope is signed package distribution, remote version discovery, and compatibility checks for the three binaries. It does not add a server-side upgrade agent or silently replace the user's OpenSSH policy.

Entry gate: define package signing, trust root, rollback, installation permissions, offline behavior, and downgrade handling. The installer must support separate binaries and the combined binary from one workspace.

Measurement gate: verify reproducible packages, signature failures, interrupted upgrades, rollback, stale process behavior, and version-skew diagnostics on supported Linux distributions.

## Candidate E: protocol evolution

Potential scope is a versioned everpty or everlink protocol revision needed for a demonstrated compatibility or security issue. It is not a route to replay, terminal state, or extra terminal semantics.

Entry gate: publish a compatibility matrix for old/new clients and servers, explicit negotiation rules, downgrade prevention, frame limits, and migration tests. Unknown versions fail closed.

Measurement gate: test every supported version pair, malformed negotiation, downgrade attempt, interrupted upgrade, and mixed-version process cleanup. An incompatible change requires a clear major-version boundary and an upgrade/rollback procedure.

## Candidate F: operational diagnostics

Potential scope is opt-in structured metrics, qlog collection, and health inspection that never captures terminal payloads, keystrokes, tokens, private keys, or full bootstrap records.

Entry gate: define fields, redaction, retention, permissions, sampling, and output destinations. Diagnostics remain off or low-volume by default and never share a byte source with PTY output.

Measurement gate: prove that diagnostics cannot block the writer or proxy, cannot change stdout, remain bounded under failure storms, and contain no forbidden data under fuzz and integration tests.

## Candidate evaluation template

Every candidate proposal must state:

- The user problem and why v1 boundaries do not solve it.
- The exact component and process boundary affected.
- The smallest protocol and dependency change.
- The security, licence, resource, and compatibility implications.
- The test fixtures, hostile-network cases, and measured acceptance criteria.
- The rollback and version-skew behavior.
- The evidence required to reject the candidate as unnecessary.

Until those gates pass, the v1 Rust design and its permanent non-goals remain authoritative.
